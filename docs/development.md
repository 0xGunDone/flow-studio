# Разработка и сборка

[← README](../README.md)

Desktop-приложение рассчитано на macOS. Backend включен в репозиторий и в релизную сборку; установка не должна ссылаться на исходный каталог разработчика.

## Запуск

Нужны Node.js 22+, Google Chrome, Docker Desktop либо Colima с Docker CLI и Docker Compose. Для сборки используйте macOS.

1. Получите исходники:

   ```bash
   git clone https://github.com/0xGunDone/flow-studio.git
   cd flow-studio
   ```

2. Установите зависимости по lockfile:

   ```bash
   npm ci --prefix app
   ```

3. Запустите Docker Desktop либо `colima start`, затем приложение:

   ```bash
   npm start --prefix app
   ```

4. Дождитесь первого запуска движка и войдите через **Аккаунты → Войти в Google**. Для обычной работы не нужны заранее подготовленная база данных или конфигурация с секретами.

Режим разработки использует пользовательскую папку Flow Studio, как установленное приложение. Не запускайте две копии одновременно и не считайте разработку изолированной от ваших аккаунтов и истории. Перед изменениями, затрагивающими формат данных, сохраните резервную копию при закрытом приложении.

## Проверки

Проверки приложения и MCP:

```bash
npm test --prefix app
node app/mcp-server.cjs --list-tools
node --test extension/tests/*.test.cjs
```

Backend использует Python и `unittest`. Для проверки backend отдельно создайте виртуальное окружение и запустите тесты из его каталога:

```bash
cd backend
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m unittest discover -s tests -p 'test_*.py'
```

Среда Python для этих тестов не нужна пользователю готового приложения: production-backend работает в контейнере. Некоторые тесты и проверки браузерного окружения могут требовать дополнительные системные зависимости; фиксируйте фактический результат, а не скрывайте пропущенные проверки.

Автоматические проверки с заглушками не подтверждают доступ Google-аккаунта или успешность платной генерации. Для ручного smoke test проверяйте запуск с чистой пользовательской папкой, вход, каталог моделей, один разрешенный пользователем запрос, экспорт результата и повторный запуск приложения. В отчете укажите архитектуру и то, что проверено вживую.

## Сборка macOS

Из корня репозитория:

```bash
npm ci --prefix app
npm run dist:arm64 --prefix app
npm run dist:x64 --prefix app
```

Обе архитектуры одной командой: `npm run dist:mac --prefix app`. Артефакты появляются в `dist/` в корне репозитория: `Flow-Studio-1.0.1-mac-arm64.zip`, `Flow-Studio-1.0.1-mac-arm64.dmg` и соответствующие файлы `x64`.

`npm run check:release --prefix app` проверяет исходники и конфигурацию упаковки. Команды сборки выполняют эту проверку, затем проверяют состав, архитектуру и ad-hoc подпись полученного `.app`. Они не публикуют артефакты автоматически.

Собирайте и проверяйте каждую архитектуру отдельно. Успешная упаковка `x64` на Apple Silicon не заменяет запуск на Intel Mac, а успешный архив не подтверждает работоспособность Docker и входа на чистом Mac.

В комплект должны входить:

- Electron-приложение и production-зависимости MCP.
- Backend с исходниками, `Dockerfile.headed` и `docker/entrypoint.headed.sh`, нужными для первого запуска.
- Лицензии приложения, Flow2API и зависимости, включая notices Electron.

Не включайте `node_modules` разработчика целиком, виртуальное окружение Python, Google-профили, `.env`, runtime-конфигурацию, базы, токены, кэш и историю генерации. Сборка должна создавать пользовательские учетные данные на машине получателя.

Сборки используют ad-hoc подпись, без Apple Developer ID и notarization. Ad-hoc подпись не означает подтвержденного Apple издателя. Не описывайте такую сборку как нотарифицированную или проверенную Apple.

## Публикация релиза

1. Обновите версию в `app/package.json`, lockfile и `CHANGELOG.md`.
2. Выполните проверки и соберите обе архитектуры.
3. Проверьте состав архивов и отсутствие секретов. Протестируйте чистый первый запуск, отдельно от существующей рабочей установки.
4. Опубликуйте GitHub Release с версией, обозначением **Alpha / Pre-release**, артефактами `arm64` и `x64`, контрольными суммами и известными ограничениями.
5. В заметках укажите необходимые Chrome и Docker, статус подписи, фактически проверенные платформы и изменения с предыдущего релиза.

Не прикладывайте реальные данные Google для демонстрации «готового входа». Сборки распространяются без пользовательских аккаунтов.

## Архитектура

```text
Интерфейс Electron ─────┐
                       ├── Runtime / аккаунты ── локальный Flow2API ── Google Flow
MCP-клиент ── stdio ── локальный мост
```

Backend слушает loopback-порт `38000`; мост MCP выбирает отдельный локальный порт и создает секрет подключения. Electron управляет жизненным циклом задач и сохраняет историю. Google Chrome отвечает за пользовательский вход и обновление управляемых сессий. Подробности протокола и поведения агента — в [MCP](mcp.md).

Изменения vendored backend сохраняйте вместе с тестом или описанием причины. Базовый upstream-коммит и условия лицензии зафиксированы в [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md).
